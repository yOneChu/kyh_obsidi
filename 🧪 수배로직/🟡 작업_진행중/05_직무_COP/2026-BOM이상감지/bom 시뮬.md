

| BOMController.simulateBlock 기능 분석

```
simulateBlock은 블록 시뮬레이터(Block Simulator) 화면의 백엔드 API입니다. 지정한 호기와 블록에 대해 지금 BOM 계산을 다시 돌리면 1레벨 BOM이 어떻게 나오는지를 계산합니다. 그 결과를 현재 EBOM과 블록 단위로 나란히 비교해서 돌려줍니다.

DB에는 아무것도 쓰지 않는 조회 전용 미리보기입니다. 실제 반영은 화면에서 /simulate/add, /simulate/delete를 따로 호출해서 합니다.

처리 흐름

1. 입력 정리 (Controller)
- productNoList: 대상 호기 목록
- blockList: 블록번호(BLOCKNO$SF.MD$NUMBER) 목록
- blockOPTList: 블록 품목(C, M, F, 1, 2, 3). 값이 있으면 이 품목에 해당하는 블록 전체를 findBLocksByOPT로 조회해서 blockList를 대신합니다. 이 경우 호기는 1개, 품목은 최대 3개까지만 받습니다.

2. 호기별 병렬 시뮬레이션 (EBOMServiceImpl.simulateBlockBatch)
- 중복을 제거한 뒤 ForkJoinPool(스레드 4개)로 호기마다 simulateBlock(productNo, blockList)를 실행합니다.

3. 시뮬레이션 값 계산 (SubaeManager.bomSimulate): 실제 BOM 계산(bomCalculate)과 같은 로직에서 DB 저장만 뺀 것입니다.
4. 호기의 공사정보(ElvMaster)와 층 정보(FloorMaster)를 읽어 사양 데이터 맵을 만듭니다.
5. EL_P 계열 PID를 계산해서 사양 값을 보강합니다. 일반, 선박, SV 엘리베이터는 각각 다른 PID 목록을 씁니다.
6. 블록마다 등록된 Pick 규칙(PICK1..n)을 하나씩 처리합니다.
   - 사양 값(예: EL_xxx)으로 자재번호를 꺼내고, 그 블록에 속한 릴리즈되고 Active인 최신 자재를 고릅니다(pickPart).
   - 수량, 주석, 도장을 PID로 계산합니다(VariableAction).
   - 하위 자재 중 공사수량(PID 패턴)이 있는 것도 따로 계산합니다(variablePartMap4Simulate).
4. 같은 자재가 여러 번 잡히면 수량은 더하고 주석은 합칩니다.
5. 수량이 0인 자재는 결과에서 뺍니다.

6. 현재 EBOM과 매칭
- 호기의 WIP 제품에서 1레벨 EBOM을 읽어 옵니다. 요청한 블록에 속한 항목만 대상으로 합니다.
- 먼저 자재번호가 같은 것끼리 짝을 짓고, 남은 것은 블록번호가 같은 것끼리 짝을 짓습니다.
- 짝이 없는 기존 BOM 행은 BOM 쪽 값만 있는 행으로 추가됩니다.
  
  
5. 결과: SimulateBomVO 목록을 호기, 블록 순으로 정렬해서 반환합니다.

결과 해석 (SimulateBomVO.getChangeType())

┌────────────┬───────────────────────────────────────────────────────────┐
│ changeType │                           의미                            │
├────────────┼───────────────────────────────────────────────────────────┤
│ SAME       │ 시뮬레이션 결과와 현재 BOM이 같음 (자재, 수량, 주석 일치) │
├────────────┼───────────────────────────────────────────────────────────┤
│ UPDATE     │ 자재는 같은데 수량이나 주석이 다름                        │
├────────────┼───────────────────────────────────────────────────────────┤
│ REPLACE    │ 같은 블록에 다른 자재가 잡힘 (자재 교체 필요)             │
├────────────┼───────────────────────────────────────────────────────────┤
│ ADD        │ 시뮬레이션에만 있음 (BOM에 추가 필요)                     │
├────────────┼───────────────────────────────────────────────────────────┤
│ DELETE     │ 현재 BOM에만 있음 (사양상 더 이상 안 잡힘)                │
└────────────┴───────────────────────────────────────────────────────────┘

화면(blockSimulator.js)은 이 결과를 왼쪽 "현재 BOM", 오른쪽 "시뮬레이션"으로 나란히 보여주고, 다른 칸은 diff로 강조합니다. 사용자는 체크한 행을 /simulate/delete(기존 BOM 링크 삭제)와 /simulate/add(시뮬레이션 자재와 공사수량 추가)로 반영합니다.

실무 용도

- 사양, PID, Pick 규칙을 바꾼 뒤 이미 BOM 계산이 끝난 호기에 어떤 영향이 있는지 미리 확인
- 전체 BOM을 다시 계산하지 않고 특정 블록만 골라 BOM을 보정
- 여러 호기에 같은 블록을 한 번에 돌려 BOM 불일치 호기 찾기

참고 (코드상 특이점)

- 135번째 줄의 NVL(...)=="" 는 문자열을 ==로 비교합니다. 그래서 null만 걸러지고 빈 문자열 ""은 남습니다. 다만 SQL이 IN ('', ...)이라 실제 결과에는 영향이 없습니다.
- blockList나 blockOPTList 키가 빠지면 NPE가 납니다. 둘 다 빈 배열로라도 보내야 합니다.
- 146~148번째 줄의 "블록 품목 선택 시 블록번호 입력 불가" 검증은 주석 처리되어 있습니다. 품목을 선택하면 입력한 블록번호는 조용히 무시됩니다.
```
